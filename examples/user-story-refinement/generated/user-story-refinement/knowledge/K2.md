## Product-Methodik: Fachliche Klärung

_Ort: notebook:The Product - Business Design_

Check a triaged request against the epic's goal and the Fachkonzept before any design work. The notebook
composes this procedure from several sources; no single source describes a step by this name.

**Inputs.** The reframed request (problem, role, benefit), the epic with its target outcome/KPIs, the
Fachkonzept (rules, domain model, ubiquitous language, NFRs) and the product vision / scope boundaries
[store-phase-2-klaerung-1: 1, 2, 5].

**Steps** [store-phase-2-klaerung-1]:

1. Separate the user need / behaviour change from any solution pre-packaged in the feedback; a feature
   request is not a problem statement [^1].
2. Map the behaviour change to the epic's outcome/KPI. The link must read feature -> user action -> epic
   KPI; a speculative or missing link means the request does not belong in this epic [^2][^3].
3. Check consistency with the Fachkonzept: no contradicting business rule, no redundancy with existing
   behaviour, no violated constraint [^4]. Pass/fail criteria for "Mit dem Fachkonzept vereinbar?" (terms,
   invariants, bounded context, domain vision) are already distilled in
   `phase-2-fachliche-klaerung.md` (Decision criteria) and `faq/triage-klaerung.md` entry
   `triage-klaerung-1` [11, 29-36]; a language conflict is a trigger to refine model and language with
   the domain experts [^5].
4. Look at affected stories/epics and components for overlaps and side effects [store-phase-2-klaerung-1: 13, 29, 30].
5. Record a disposition: accept into the epic, re-frame or split, or reject/defer [store-phase-2-klaerung-1].

**Deciding "serves the epic's target outcome"** [store-phase-2-klaerung-1: 11, 45, 52]:

- Outcome over output: a delivered feature that does not change behaviour does not serve the goal [^6].
- The expected effect on the KPI must be measurable after delivery [^7].
- Weigh value against cost: "mission critical" and "market differentiating" are the two triage questions [^8].

**Output.** The request (or its story draft) with its epic link and a recorded decision. Rejected items go
on a log with the reason, so a later look-alike request can be matched against it [^9].

**Pitfalls the notebook names** [store-phase-2-klaerung-1: 4, 22, 60, 67, 68, 72, 76]:

- Taking the request at face value without asking "why"; gold-plating features with no use case [^10].
- Treating an epic as a bucket topic ("reporting") instead of a bounded, goal-oriented milestone [^11].
- Stream-of-consciousness planning: deliverable first, justification ("In order to...") invented afterwards [^12].
- Checking without all relevant perspectives: "Jede übersehene Perspektive birgt das Risiko späterer Nacharbeiten" [^13].

**Not answered by the sources.** No numeric threshold is given for "moves the KPI enough"; the decision stays a judgement call for the PO and the team.
