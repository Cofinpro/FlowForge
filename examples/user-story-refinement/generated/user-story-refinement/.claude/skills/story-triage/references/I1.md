## Product-Methodik: Eingang & Triage

_Ort: notebook:The Product - Business Design_

_Footnotes name the notebook source. The verbatim quotes and FAQ references stay with the generation output (`knowledge/`), which is not installed._

Task "Feedback erfassen & als Problem formulieren". Related decisions (bug or story, how it relates
to the backlog) are in `domain-knowledge.md`; they are not repeated here.

**What to record about the feedback.** The notebook gives no single intake form. The fields below are
collated from several sources:

- Channel (support desk, email, forum, review, sprint review) and how often / how many users it
  affects [^1][^2].
- Sender and role. Separate end users from managers or proxies; a manager's report can be inflated, so
  corroborate it with real users [^3].
- The sender's exact words, not a paraphrase. Quotes are weak evidence but give context [^4].
- Today's workaround: "How is it solved today?" [^5].
- Reach and cost of waiting: how many users, which company goal, what happens if it is not addressed
  in two weeks / six months, who to ask for details [^1].

**Steps from request to problem.**

1. Restate the request in your own words and ask what it would let the sender do. Then ask "why"
   repeatedly (up to five times) until the root pain shows; the "magic wand" question ("If you could
   wave a magic wand and be able to do anything you can't do today, what would it be?") bypasses
   solution thinking [^6][^7].
2. Fill in the problem context: what is the problem and why is it one, who has it, when and where does
   it occur, how is it solved today [^5].
3. State the problem as a behaviour change, never as a feature. "Get a profit overview faster", not
   "Cash report" [^8]. Add a contrast clause, "Whereas currently…" or "Instead of…" [^9], and ask
   "How much?" so the change is observable and measurable [^10].

**Output** (any one is fine; the notebook offers several): a problem statement for an existing product
(goals, where they are not met, a request for improvement that names no solution) [^11], a "How might
we" question [^12], or a behavioural user story "In order to … as a … I want …" [^8][^9].

Worked example from the sources: a request for faster customer reports turned out to be a need to find
data discrepancies; the story became "In order to resolve customer data discrepancies faster…" [^13].

**Checks before passing the problem on.**

- Does it name a user need or behaviour change rather than a UI or technical solution? A feature wish
  as a "problem statement" is only a hidden requirement [^14][^15].
- Is there a specific role, not "As a user…"? Generic roles let pet features through [^16].

**Pitfalls.**

- Writing down "Users want feature X" without asking why; this lets users design the product [^7].
- Feedback is skewed: people write when they are delighted or furious, and a single report says
  nothing about the sender's value to the business [^17]. Support-desk requests lean towards small
  incremental changes and beginners' problems [^18].

**Terms.**

- *Problem space / solution space*: needs, pains and jobs live in the problem space; mockups and
  products live in the solution space. Start in the problem space [^19].
- *Behaviour change*: the outcome written as a measurable change in what people do, not as a delivered
  software feature [^8].
- *How might we*: the problem written as an open design question, "How might we help [persona] do
  [goal] in [context] so that [outcome]?" [^12].

**Not covered by the notebook.** A fixed record format for feedback, who must acknowledge the sender,
and how to deduplicate identical feedback items are not described.
