## Product-Methodik: Story formulieren

_Ort: notebook:The Product - Business Design_

_Footnotes name the notebook source. The verbatim quotes and FAQ references stay with the generation output (`knowledge/`), which is not installed._

**Task: "Story im Connextra-Format formulieren".** Output: one story card "As a [role] I want [goal] so that [benefit]".

### Who and how

- The customer side (Product Owner, Business Analyst) writes the card; developers help so it stays testable and sized [^1].
- Template: "I as a (role) want (function) so that (business value)" [^2]. It is a discussion token, not a mandatory form: if another wording starts a better conversation, the card has done its job [^3].

### The three parts

- **As a [role]:** a concrete role or persona, never "a user" [^4]. Write "A Geographic Searcher can restrict his job searches…", not "A user can…" [^5]. A system or a team member is not a role (fake story) [^6].
- **I want [goal]:** the capability, no UI or technology. Do not write "The system will use Log4J…"; write what the user gets, e.g. "Whenever an error occurs, users are given enough information to know how to correct the error." [^7]
- **so that [benefit]:** describe an observable change in behaviour, not what the software does [^8][^9]. Ask "How much?" and quantify, or give a range [^10]. "in order to improve business" becomes "in order to monitor inventory 50% faster" [^11]. Benefits start from the customer's view ("I", "my") with a verb such as reduce, increase, save [^12]. Write it so it can be tested for outcome after delivery [^13].

### Good and bad examples from the sources

- Good: "As a shopper, I want to be able to filter my search results by price range, so that I can easily find products that are within my budget." [^14]
- Bad, fake story: "As a QA, in order to test faster, I want the database server restarts to be automated" [^6]
- Bad, circular: "As a user I want to register so that I can log in" ("A user of a website never wants to register.") [^15]
- Bad, solution as need: "in order to run reports faster, I want the customer reporting database queries to be optimised". The real need was resolving data discrepancies faster [^16].

### Card, not contract

The card is a reminder for a conversation; "the conversation is the key, not the note on the story card" [^17]. Details go into acceptance tests (see C4).
