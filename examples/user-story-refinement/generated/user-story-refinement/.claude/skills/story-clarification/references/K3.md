## Product-Methodik: Fachliche Klärung

_Ort: notebook:The Product - Business Design_

_Footnotes name the notebook source. The verbatim quotes and FAQ references stay with the generation output (`knowledge/`), which is not installed._

Describe how the system behaves today versus after the story, plus the behaviour change and a measurable
target. The notebook composes the procedure from several sources; it gives the building blocks, not a
fixed template for an "ist-soll-delta" artifact.

**Inputs.** The documented current behaviour (rules, flows, outputs), the feedback/incident data behind the
request, the underlying user need, and the affected role.

**Steps** [store-phase-2-klaerung-2]:

1. Establish the current condition from facts and data, not assumptions [^1]. Ask the stakeholders what
   the target is, not only what they do today, or outdated practice gets documented as the Ist [^2].
2. State the behaviour change: what users will do differently, not what the software does [^3].
3. State the system delta: how functionality or business rules differ between now and after the story,
   as observable outputs, not implementation details [^4].
4. Set a measurable target: baseline, expected change (a range), and an acceptance criterion [^5][^6].
5. Check for unstated cases, for example what happens when a condition is not met [^7].

**Writing the delta.** Add a "Whereas currently..." or "Instead of..." clause after "I want...". Test the
verb with a negative question ("Is it true you cannot do this today?"); if a workaround exists, the verb is
wrong [^8]. Why it matters: the effort depends on how far the target differs from today's behaviour [^9].

**Measurable target.** Ask "How much?" once the change is named; if a single value is hard, set a range
between the minimum that is still valuable and the "over the top" level [^5]. One key metric against a
baseline, e.g. reduce 22 major issues by 20% [^6]. The expected behaviour change is also what yields the
acceptance criterion. A criterion must be provable by a test or measurement [^10].

**Output.** A story-level statement with role, behaviour change ("In order to..."), the system delta
("instead of..."), acceptance criteria with metric and baseline, and an explicit out-of-scope ("features
out") list [^11].

**Pitfalls the notebook names**:

- A feature request without context: "Cash report" is not a summary, a behaviour change is [^12].
- The current state left undocumented, so the effort is misjudged [^9].
- Vague goals ("faster", "user-friendly") without a baseline or number.
- Missing else-branch of a condition [^7].
- Fake technical stories ("As a developer, I want to understand how the new external API works") [^13].

**Terms.** Ist-/Soll-Zustand (current vs target behaviour); Abnahmekriterium (testable acceptance
condition); Entscheidungstabelle (decision table to find missing cases); Nominalisierung (a process hidden
in a noun, to be defined in a glossary).

**Not answered by the sources.** No fixed format or length for the delta description; the sources do not
say how to obtain the baseline value when no analytics exist.
