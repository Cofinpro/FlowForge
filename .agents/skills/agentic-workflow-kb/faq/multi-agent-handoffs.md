## multi-agent-handoffs-1: How do agents hand off work, and how do multi-agent systems fail?

**Question**

> In multi-agent systems, how should agents communicate and hand off work according to the sources? Cover: message or contract formats between agents, structured outputs, shared state versus message passing, handing off via artifacts/files, context passed at handoff, coordination and conflict resolution, and the most common failure modes of multi-agent systems (e.g. error propagation, infinite loops, lost context, role confusion, cost explosion) with their mitigations.

**Answer** (verbatim, citation markers resolve in the table below)

In multi-agent systems (MAS), designing how agents communicate, hand off state, and resolve conflicts is critical for building reliable, production-grade applications [1]. Grounded in the architectural guides and engineering standards from your sources, here is a detailed overview of inter-agent communication, handoff mechanics, state paradigms, coordination strategies, and failure mitigations.

---

##### 1. Message and Contract Formats Between Agents

When agents interact across system boundaries or within an orchestration network, standardized protocols prevent brittle custom glue code [2].

* **Agent-to-Agent (A2A) Protocol:** Developed as an open standard for cross-platform agent collaboration, A2A handles communication between heterogeneous or "untrusted" agents [3, 4].
  * **Discovery via Agent Cards:** Agents expose metadata at `/.well-known/agent.json` (Agent Cards) detailing capabilities, endpoint URLs, and auth requirements [5, 6].
  * **Handshake & Negotiation:** Agents perform a handshake to verify protocol compatibility (e.g., version matching, capability checks) before exchanging work [7].
  * **Transport & Framing:** Uses JSON-RPC 2.0 over HTTPS, WebSockets, or gRPC [5]. Tasks move through typed lifecycle states (`submitted`, `working`, `input-required`, `completed`, `failed`, `canceled`) with unique IDs [6].
* **Model Context Protocol (MCP):** Acts as a uniform interface connecting agents to external tools, databases, and microservices via JSON-RPC 2.0 [2, 8]. It injects dynamic context directly into the model's reasoning process without requiring bespoke API adapters [9, 10].
* **Typed Data Interfaces (Pydantic / TypedDict):** Internal agent runtimes use strictly typed Python objects or JSON schemas to guarantee that inputs and outputs match expectations between graph nodes or process steps [11-13].

---

##### 2. Structured Outputs

Relying on raw natural language between subagents causes parsing failures and cascading errors [14, 15]. Sources emphasize **structured outputs** as the foundation for typed pipelines:

* **Specification-Based Output:** System prompts define exact JSON return schemas or XML tool-call wrappers (e.g., `<tool_call>{"name": "...", "arguments": {...}}</tool_call>`) [16, 17].
* **Schema Validation & Automatic Retry Loops:** Modern orchestration harnesses (such as dynamic JavaScript workflows or LangGraph) enforce JSON Schema or Pydantic validation [12, 14]. If a subagent returns invalid JSON, the runtime catches the validation error and automatically executes a retry prompt with correction details before handing off to the next stage [18, 19].
* **Type-Safe Field Access:** Enforcing structured output schemas ensures downstream agents can destructure specific fields (e.g., `result.affectedModules` or `verdict.isReal`) without fragile regular expressions [14, 20].

---

##### 3. Shared State vs. Message Passing

Multi-agent architectures manage state and messaging using two primary models:

```
  SHARED STATE / BLACKBOARD PARADIGM             MESSAGE PASSING / SWARM PARADIGM
  +-----------------------------------+          +-----------------------------------+
  |      Centralized State Bus        |          |  [Agent A]                        |
  |   (TypedDict / Checkpoint Store)  |          |     |                             |
  |     ^                       ^     |          |     v (Handoff Tool Call)         |
  |     | (Write)               | (Read)         |  [Agent B]                        |
  |  [Agent 1]               [Agent 2]|          |     | (Direct Payload/Context)    |
  +-----------------------------------+          +-----------------------------------+
```

###### Shared State Architecture (Blackboard Pattern)
* **Centralized State Bus:** All subagents read from and write to a unified snapshot schema (e.g., a LangGraph `TypedDict` or Pydantic `BaseModel`) [11, 12]. Nodes execute pure state transitions, appending messages or updating specific state keys [11, 21].
* **Thread Checkpointing & History:** Persisted via memory savers or database checkpointers attached to a `thread_id` [22, 23]. Execution can pause for human review and resume from exact substate checkpoints without re-running earlier nodes [22, 24, 25].
* **Decoupled Event Buses:** In distributed microservice deployments, shared state is managed via append-only message brokers (Kafka, Redis Streams, NATS) [26-28]. A supervisor agent publishes tasks to a topic, and specialist worker processes consume events, process them in isolated execution loops, and publish responses back [26, 28, 29].
* **Actor Frameworks (Ray / Orleans):** Stateful actors encapsulate both computation and session-isolated memory, processing tasks sequentially per session to prevent shared-state race conditions [30-32].

###### Message Passing Paradigm (Peer-to-Peer / Swarm)
* **Direct Control Handoffs:** Agents shift execution dynamically using explicit handoff tools created via helpers like `create_handoff_tool` [33, 34].
* **Dynamic Control Flow:** For example, a `research_assistant` calls `transfer_to_writer` when research is complete; if the writer finds evidence lacking, it invokes `return_to_researcher` to pass control back [35, 36].

---

##### 4. Handing Off via Artifacts and Files

To keep context windows small and avoid token bloat, agents should hand off work using **file artifacts** on disk or in version control rather than dumping large payloads into prompts [37-39].

* **Structured File Storage (`PLAN.md`, `changes.json`):** An orchestrator agent writes progress to structured files (e.g., `PLAN.md` or a JSON diff file) [37, 40, 41]. Downstream agents read or update the file on demand [37].
* **Plan-Validate-Execute Pattern:** For batch or destructive edits, an agent writes a `changes.json` plan file [41]. A deterministic validation script verifies the file first; only upon passing validation does the execution agent apply the changes [41].
* **Git Worktree Isolation:** When multiple agents generate or edit code in parallel, each agent runs in an isolated git worktree copy of the repository to prevent file modification collisions and race conditions [14, 42].

---

##### 5. Context Passed at Handoff

Passing entire conversation histories at every handoff triggers "context rot" and degrades model performance [43, 44]. Context transfer requires deliberate **context engineering** [43, 45]:

* **Minimal Viable Context:** Handoffs should pass only the target agent's system prompt, the immediate task instructions, and references to relevant artifacts or summaries [37, 46, 47].
* **Context Cropping & Filtering:** When transitioning phases, crop out intermediate multi-turn tool chatter, leaving only the primary goal and structured plan file (`PLAN.md`) [37].
* **Memory Processors & Sliding Windows:** Use memory processors (e.g., `TokenLimiter` to prune old messages and `ToolCallFilter` to strip raw tool outputs) or sliding message windows (`lastMessages: 6`) alongside RAG-based semantic recall (`topK`) [48, 49].

---

##### 6. Coordination and Conflict Resolution

* **Manager / Supervisor Coordination:** A central supervisor agent evaluates queries, dispatches tasks to specialist workers based on query intent, and synthesizes outputs [50-52]. This avoids deadlocks and establishes a clear audit trail [52, 53].
* **Hierarchical Teams:** Supervisors manage sub-teams (e.g., an executive supervisor routing between a Research Team graph and a Writing Team graph), scaling organizationally while maintaining local guards and rate limits [54-56].
* **Democratic / Consensus & Judge Panels:** Multiple independent subagents score or generate candidate solutions concurrently [57, 58]. A synthesis or judge agent evaluates the candidates [58, 59]. If the score variance among judges exceeds a threshold, additional reflection cycles are triggered until consensus is reached [60].
* **Single-Threaded Linear Fallback for Conflicting Parallel Tasks:** When parallel subagents operate without shared context on interdependent tasks, they often generate mutually incompatible outputs (e.g., one agent designing a high-speed platformer control scheme while another designs a puzzle path system requiring stopping) [61, 62]. The solution is to fall back to a **single-threaded linear agent** thread where subtasks execute sequentially with shared context [61, 63].

---

##### 7. Common Failure Modes and Mitigations

Multi-agent interactions introduce non-deterministic systemic failure modes [64-66]. The table below summarizes these common failure modes alongside their primary mitigations:

| Failure Mode | Cause / Impact | Recommended Mitigation Strategy |
| :--- | :--- | :--- |
| **Error Propagation & "Coherent Incorrectness"** | An agent misinterprets initial requirements or generates flawed code; downstream agents build their entire logic on that misunderstanding, producing code that is internally consistent but fundamentally wrong [61, 67]. | • Implement **Plan-Validate-Execute** workflows with deterministic validator scripts [41].<br>• Use **Evaluator-Optimizer / Reflection loops** to verify candidates against explicit rubrics before handoff [59, 68].<br>• Feed raw execution errors back into the agent context so it fixes its own mistakes [69, 70]. |
| **Infinite Loops & Runaway Execution** | Agents cycle continuously without reaching a termination condition, or swarm agents repeatedly hand work back and forth [33, 71]. | • Enforce strict **recursion limits and step bounds** on graph state transitions [71].<br>• Implement **budget guards** (`while (budget.remaining() > 50_000)`) in orchestrator loops [72, 73].<br>• Track item deduplication sets across iterations (including rejected items) to prevent cyclic re-processing [58]. |
| **Context Rot, Poisoning & Confusion** | As context window size exceeds 100k tokens, accuracy degrades ("context rot") [43, 44, 74]. Irrelevant context causes "context confusion", and hallucinated errors persist as "context poisoning" [74]. | • Apply **progressive context compaction/summarization** when approaching token capacity limits [44, 48, 75].<br>• Use **file-backed artifacts** (`PLAN.md`) and crop raw execution history during handoffs [37, 46].<br>• Filter memory with `ToolCallFilter` and top-K RAG recall [48, 49, 76]. |
| **Role Confusion & Overloaded Prompts** | Giving a single agent too many tools (>10–16 tools) overloads its prompt, causing tool selection errors and argument hallucinations [77-79]. | • Adhere to the **Single Responsibility Principle** by splitting monolithic agents into narrow specialist subagents [51, 80, 81].<br>• Write subagent descriptions strictly in the **third person** to ensure accurate supervisor routing [50, 82]. |
| **Cost Explosion & Token Bloat** | Uncontrolled multi-agent fan-outs, verbose messages, or repeated full-context handoffs rapidly burn through token budgets [15, 83, 84]. | • Use **zero-token orchestrators** (e.g., JavaScript dynamic workflow scripts) for pipeline control flow [85, 86].<br>• Route routine classification/extraction subtasks to lightweight models (e.g., GPT-4o-mini, Haiku) [87, 88].<br>• Enable **prompt caching** and enforce strict token concurrency caps [19, 44]. |
