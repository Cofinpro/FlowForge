## context-engineering-1: How do I keep an agent's context lean and effective?

- asked 2026-09-26 · notebook "Agentic Workflows" · conversation `dfe58cb3-6429-4d15-800d-9572b2497b29`
- Sources: Grootendorst & Alammar, An Illustrated Guide to AI Agents (O'Reilly, 2025); Albada, Building Applications with AI Agents (O'Reilly, 2025); Bhagwat & Gienow, Patterns for Building AI Agents (2026); Context windows - Claude Platform Docs; Bhagwat, Principles of Building AI Agents; Osmani, My LLM coding workflow going into 2026 (addyosmani.com); Skill authoring best practices - Claude Platform Docs; Bruniaux, claude-code-ultimate-guide: dynamic-workflows.md (GitHub); VoltAgent awesome-claude-code-subagents, 09-meta-orchestration (GitHub)

**Question**

> What do the sources say about context engineering for agents? Cover: context window limits and how Claude's context window works (token budget, extended thinking, tool results, context awareness), context rot / degradation with long context, what to load up front versus on demand, compaction and summarization, short-term vs long-term memory, using subagents to isolate context, passing only the needed context between agents, and practical rules for keeping context lean.

**Answer** (verbatim, citation markers resolve in the table below)

**Context engineering** refers to the discipline of dynamically selecting, structuring, and assembling all inputs—system prompts, user queries, retrieved knowledge, tool schemas, and conversation history—into a structured, token-efficient context window [1-3]. As Andrej Karpathy notes, context engineering is both an art and a science: a science because it integrates concrete technical domains (RAG, prompt engineering, tool calling, state management), and an art because it requires human intuition regarding how language models process information [3].

Building reliable agents requires solving a "Goldilocks problem": providing too little context leaves the model blind, while providing too much or irrelevant context causes the agent to lose its way [4].

---

##### 1. Context Window Limits and Claude's Architecture

The **context window** functions as the model's working memory for a single call [5, 6]. Standard models range from 200k tokens up to 1M tokens (such as Claude Sonnet 5, Sonnet 4.6, Sonnet 4.5, and Opus models) or even 2M tokens (Google Gemini) [5, 7, 8]. 

In Claude's API architecture, context works through **progressive token accumulation**, where every turn's input and output carry forward into subsequent turns [9].

* **What counts toward the token budget:** Everything in the request counts against the capacity limit—the system prompt, raw conversation history, tool schemas, images/documents, tool results, generated responses, and extended thinking tokens [10, 11].
* **Extended thinking:** Thinking tokens are billed as output tokens and count toward context limits [11]. On newer models (such as Claude Opus 4.5+ and Sonnet 4.6+), thinking blocks from previous assistant turns are preserved by default and count as input tokens; on other models, the API automatically strips previous thinking blocks to save space [12, 13].
* **Tool use with thinking:** When passing tool results back to Claude, the client must include the unmodified thinking block that accompanied the tool call request [14]. Models with **interleaved thinking** can also generate new thinking blocks between consecutive tool calls [15].
* **Context awareness:** Certain models (e.g., Claude Sonnet 5, Sonnet 4.6, Sonnet 4.5) possess built-in context awareness [16]. The API automatically injects system tags (such as `<budget:token_budget>200000</budget:token_budget>`) at the start of a session and sends token usage updates after tool calls (e.g., `<system_warning>Token usage: 35000/200000; 165000 remaining</system_warning>`), allowing the model to manage its remaining capacity during long-running tasks [16, 17].

---

##### 2. Context Rot and Degradation

Arbitrarily filling massive context windows leads to performance degradation—a phenomenon known as **context rot** [6, 18, 19].

* **Retrieval vs. Reasoning Degradation:** Early benchmarks like "Needle in a Haystack" (NIAH) showed strong retrieval across long windows [20, 21]. However, complex reasoning benchmarks (such as RULER) reveal that multi-hop reasoning, aggregation, and task accuracy drop sharply as context length increases [18, 21]. Benchmarks on complex tasks show accuracy degrading significantly once prompts exceed ~100k–125k tokens, even on models with 500k+ windows [19, 22].
* **The "Lost in the Middle" Effect:** Models exhibit a serial-position effect, paying more attention to information placed at the very beginning (primacy effect) or end (recency effect) of a prompt, while missing details buried in the middle [23, 24].
* **The 5 Context Failure Modes:**
  1. **Context Poisoning:** An error or hallucination enters the context and is repeatedly referenced in subsequent turns [19].
  2. **Context Distraction:** Context becomes so long that the model overfocuses on prompt details and discounts its underlying pre-trained knowledge [19].
  3. **Context Confusion:** Irrelevant context leads to lower-quality or off-target responses [19].
  4. **Context Clash:** Newly introduced information conflicts with earlier statements in the prompt [19].
  5. **Context Rot:** Large token counts degrade the model's ability to distinguish noise from critical signals [19].
* **Cost and Latency:** Larger contexts dramatically increase latency and VRAM/token costs, making uncurated context dumps impractical for production [25-27].

---

##### 3. What to Load Up Front vs. On Demand

* **Load Up Front (Static Context):** High-level goals, system prompt instructions, core invariants, user specifications, and baseline constraints [28-30]. Performing a "brain dump" or providing specification files (`spec.md`, `PLAN.md`) up front ensures the model is grounded in the exact rules and non-negotiable facts before execution begins [30-32].
* **Load On Demand (Dynamic Context):** Avoid dumping whole databases or codebases into context [33, 34]. Instead, fetch relevant documentation, past interactions, or code snippets lazily using **RAG**, BM25 full-text search, or vector stores [34-37].
* **Progressive Disclosure:** For system skills and tools, only metadata (names and short descriptions) is pre-loaded at startup [38]. Detailed instruction files (`SKILL.md`) or helper scripts are read on demand only when the specific capability becomes relevant [38].

---

##### 4. Compaction, Summarization, and Pruning

To keep long-running conversations within budget, agents rely on context editing and compression [27, 39]:

* **Server-Side Compaction:** Automatically summarizes earlier parts of the conversation on the server when approaching context limits (e.g., Claude's server-side compaction or Claude Code's autocompact at 95% capacity) [6, 39, 40].
* **Rolling Summarization & History Cropping:** An LLM periodically compresses the conversation history into a running summary while cropping out raw multi-turn messages [31, 41, 42]. Older interaction turns are dropped, leaving only the system prompt, current state/summary file, and immediate user query [31].
* **Pruning and Filtering:** 
  * **Tool Result Clearing:** Stripping or truncating voluminous tool outputs once they have been processed [40, 43].
  * **Thinking Block Clearing:** Stripping prior extended thinking traces on models that do not drop them automatically [12, 43].
  * **Memory Processors:** Using tools like Mastra's `TokenLimiter` (removes oldest messages) and `ToolCallFilter` (strips historical tool calls before passing context to the LLM) [40, 44].
* **Redundancy Reduction (MMR):** Using Maximal Marginal Relevance (MMR) or deduplication algorithms to ensure retrieved context chunks contain novel information rather than redundant paraphrases [45, 46].

---

##### 5. Short-Term vs. Long-Term Memory

Agent architectures categorize memory into distinct cognitive types [47]:

| Memory Type | Scope & Definition | Implementation Methods |
| :--- | :--- | :--- |
| **Short-Term (Working Memory)** | Immediate context for ongoing interactions; holds chat history, current user queries, and internal reasoning steps [48-50]. | Rolling message arrays, in-memory state graphs, local session state [48, 51, 52]. |
| **Episodic Memory** | Long-term memory of specific past events, actions taken by the agent, and their outcomes [48, 53]. | Trace logs, execution histories, structured case databases [53, 54]. |
| **Semantic Memory** | Long-term general world knowledge, facts, and enterprise documentation [53, 55]. | Vector databases, RAG, knowledge graphs (GraphRAG) [35, 37, 53]. |
| **Procedural Memory** | Rules and learned behaviors governing *how* the agent performs tasks [55, 56]. | System prompts, hardcoded workflows, parametric weights [55, 56]. |

Specialized long-term memory architectures include **MemoryBank**—which uses an Ebbinghaus-inspired forgetting curve to reinforce frequently accessed memories and prune unused ones [57, 58]—and **A-MEM**, which structures memory as interconnected, evolving atomic notes [59, 60].

---

##### 6. Isolating Context with Subagents

A major architectural pattern is transitioning from **monolithic "mega-agents"** (which carry dozens of tools and broad instructions) to **orchestrated specialists (subagents)** [61, 62].

* **Why Subagents Prevent Context Failure:** Single mega-agents suffer from tool selection errors and prompt distraction when given huge system prompts and tool sets [62, 63]. Splitting a workflow into specialist subagents (e.g., an inventory agent, shipping agent, and supplier agent) isolates the context window for each subagent [64, 65].
* **Zero-Cost Orchestrators:** In dynamic workflow engines (such as Claude Code dynamic workflows), a JavaScript script acts as an orchestrator at zero token cost, spawning separate `agent()` calls where each subagent receives its own isolated context window [66, 67].

---

##### 7. Passing Context Between Agents

When subagents collaborate, passing context requires careful boundary control [68, 69]:

* **Structured Handoffs:** Rather than passing the entire conversation trace, a supervisor or coordinator agent extracts key messages, user constraints, or intermediate outputs, passing only the necessary parameters to downstream specialists [68, 70].
* **Trace Sharing vs. Strict Isolation:**
  * *With Full Trace Sharing:* Subagent B receives Subagent A's full execution trace (e.g., seeing research and user approvals behind a design choice), ensuring full alignment [71].
  * *With Strict Isolation:* Frameworks like Claude Code intentionally run subagents with completely isolated context windows, requiring all relevant information to be explicitly specified in the subagent prompt [67, 72].

---

##### 8. Practical Rules for Keeping Context Lean

1. **Filter with Top-K and Re-ranking:** Use vector search, BM25, or re-rankers to select only the top \\(K\\) most relevant context chunks rather than raw document dumps [34, 36, 73].
2. **Place Critical Context at the Margins:** Position vital instructions, constraints, or retrieved facts near the top of the system prompt or near the very end of the prompt to combat "Lost in the Middle" degradation [23, 52].
3. **Structure Context explicitly:** Compile context into structured object schemas (e.g., explicit fields for `goal`, `returnFormat`, `warnings`, `contextDump`) before invoking the LLM [34].
4. **Prune Intermediate Tool Outputs:** Clear verbose tool execution results once their findings have been synthesized into state [40, 43].
5. **Practice Concise Prompting:** Assume the model possesses strong baseline reasoning; do not waste tokens explaining common concepts or providing unnecessary background [38, 74].
