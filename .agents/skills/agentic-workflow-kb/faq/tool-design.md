## tool-design-1: How should tools and MCP servers for agents be designed?

- asked 2026-09-26 · notebook "Agentic Workflows" · conversation `ee36d0a1-072d-4b80-8f61-c1ad4ef64c11`
- Sources: Albada, Building Applications with AI Agents (O'Reilly, 2025); Bhagwat, Principles of Building AI Agents; Skill authoring best practices - Claude Platform Docs; Koenigstein, AI Agents: The Definitive Guide (O'Reilly, 2025); Grootendorst & Alammar, An Illustrated Guide to AI Agents (O'Reilly, 2025); Osmani, My LLM coding workflow going into 2026 (addyosmani.com); Bhagwat & Gienow, Patterns for Building AI Agents (2026); Osmani, Beyond Vibe Coding (O'Reilly, 2025); Bruniaux, claude-code-ultimate-guide: dynamic-workflows.md (GitHub)

**Question**

> How should tools be designed for AI agents according to the sources? Cover: writing tool names and descriptions, input schemas, granularity (few powerful vs many narrow tools), how many tools an agent should have, returning useful errors, MCP (Model Context Protocol) servers, permissions and least privilege, sandboxing, and when to use a deterministic script or code instead of an LLM step.

**Answer** (verbatim, citation markers resolve in the table below)

Based on the sources, tool design is one of the most critical factors determining the reliability, safety, and performance of AI agents [1, 2]. Below is a comprehensive breakdown covering each aspect of agent tool design:

---

##### 1. Writing Tool Names and Descriptions
* **Precise, Semantic Naming**: Tool names should be concise, clear, and semantically descriptive of their exact function (e.g., `calculate_sum` or `multiplyNumbers` rather than ambiguous names like `process_numbers`, `doStuff`, `helper`, or `utils`) [3-6]. Action-oriented, lower-case, hyphenated, or gerund forms (e.g., `managing-databases`, `analyzing-spreadsheets`) make tools easy to identify and discover [6].
* **Third-Person, Distinctive Descriptions**: Tool descriptions (often derived from function docstrings or YAML metadata) are mandatory in frameworks like LangChain and serve as the model’s primary instructions for tool selection [3, 6-8]. Descriptions must be written in the **third person** (e.g., *"Processes Excel files and generates reports"* rather than *"I can process Excel files"*) and include a clear summary of unique purpose, key trigger terms, and parameter definitions [3, 4, 6].
* **Concrete Examples**: Including concrete example invocations (showing typical input parameters and expected outputs) inside the tool description grounds the LLM’s understanding and prevents ambiguous misfires [4].

---

##### 2. Input Schemas and Constraints
* **Machine-Readable Contracts**: Tools should define explicit input and output schemas using structured standards like JSON Schema, Zod, or Pydantic [5, 9, 10]. These define parameter names, exact data types (integers, strings, floats), required fields, and acceptable ranges [4, 5, 9].
* **Strict Constraints**: Defining strict parameter boundaries (e.g., specifying that integers must fall between 0 and 1,000) helps the foundation model evaluate parameter fit and rule out irrelevant tools [4, 10].
* **Pre-Execution Validation**: Runtime validation layers (e.g., using Pydantic or Ajv) should inspect proposed tool call parameters against the schema before execution [10-12]. If malformed inputs or missing fields are detected, the system catches them early and prompts the LLM to correct its payload before invoking the underlying endpoint [10-12].

---

##### 3. Tool Granularity: Few Powerful vs. Many Narrow Tools
* **Favor Narrow, Atomic Tools**: Tools should be narrowly scoped and encapsulate a single, well-defined function (e.g., `get_user_profile(user_id)` or `add_new_customer(record)`) rather than exposing monolithic, broad capabilities (e.g., an *"execute arbitrary SQL"* endpoint) [3, 13]. Overloaded tools with dozens of parameters confuse language models and dramatically increase security and execution risks [3, 13, 14].
* **Managing Selection Overhead**: While narrow tools increase reliability for individual actions, having dozens of granular tools can lead to description overlap and semantic collisions during tool selection [4, 15-17]. To resolve this trade-off, developers use structured indexing strategies (such as vector-based retrieval or hierarchical groupings) [15, 17-19].

---

##### 4. How Many Tools an Agent Should Have & Scaling Strategies
* **Keep Tool Count Small**: As a general rule, developers should **minimize the number of tools** bound directly to a single agent [3, 14, 16]. When an agent is tasked with choosing from a large toolset (e.g., 16+ tools simultaneously), performance and selection accuracy degrade significantly due to option overload and context window saturation [14, 16, 17].
* **Scaling Beyond Small Toolsets**: When an application requires extensive capabilities, use one of three architectural patterns:
  1. **Semantic Tool Selection**: Index tool schemas in a vector database (e.g., FAISS) using embeddings. At runtime, perform a semantic search to retrieve only the top \\(K\\) relevant tools for the LLM context window [17, 18, 20, 21].
  2. **Hierarchical Tool Selection**: Organize tools into logical groups (e.g., *Computation*, *Automation*, *Communication*). The agent first selects the appropriate category and then picks the specific tool within that subgroup [17, 19, 22].
  3. **Multi-Agent Decomposition**: Split a massive toolset across specialized sub-agents (e.g., an *Inventory Specialist*, a *Transportation Specialist*, and a *Supplier Specialist*), each bound to a small, focused set of tools under a supervisor coordinator [17, 23, 24].

---

##### 5. Returning Useful Errors & Execution Feedback
* **Feed Errors into Context**: When tool execution fails, raises an exception, or yields a linter/compiler error, the raw error output should be pushed directly back into the conversation history as a tool observation message [25-29].
* **Iterative Self-Correction**: Providing the exact error message alongside the prior code/parameters allows the LLM to inspect what went wrong, adapt its parameters, and attempt a fix in the next iteration [25, 27, 29, 30].
* **Loop Protection**: Tool execution loops must be bounded by a maximum step budget or retry limit to guard against infinite loops if an error cannot be resolved [25, 31, 32]. Repeated failure patterns should be incorporated back into the system prompt as negative constraints [29].

---

##### 6. Model Context Protocol (MCP) Servers
* **The "USB-C Port for AI"**: MCP is an open standard developed by Anthropic (and widely adopted across major AI frameworks) that standardizes how language models connect to external tools, databases, and APIs [33-35]. It solves the \\(N \times M\\) integration problem (where every LLM required custom glue code for every tool) by creating a uniform \\(N + M\\) architecture [34, 36, 37].
* **Architecture & Components**:
  * **MCP Server**: A lightweight program or web service exposing methods and resources over JSON-RPC 2.0 (via STDIO, HTTPS, or WebSockets) [34, 38, 39].
  * **MCP Client**: A connector residing in the host application that maintains 1-to-1 connections with servers, fetches tool catalogs, and handles request forwarding [38, 40, 41].
  * **MCP Host**: The overarching LLM application (e.g., Cursor, Claude Code, GitHub Copilot) that orchestrates interactions between the model and client tools [40, 42, 43].
* **Key Benefits**: Centralized maintenance (API maintainers update the MCP server once, and all connected clients benefit without custom adapter rewrites) and dynamic tool discovery across different development ecosystems [37, 44, 45].

---

##### 7. Permissions, Least Privilege, and Guardrails
* **Principle of Least Power**: Grant the agent only the minimum tools and capabilities strictly required for its task [13, 46].
* **Read/Write Separation**: Agents needing information lookup should never be granted update or deletion privileges [13]. Stateful and destructive operations (e.g., modifying production databases or issuing refunds) must be isolated from read-only paths [13, 47].
* **Granular & Just-in-Time Access**: Move away from broad role-based permissions toward just-in-time credentials granted on a per-tool-call basis [47].
* **Restricted Planning Modes**: Implement operational modes (e.g., a "planning mode") where mutation commands (like SQL `UPDATE` or `DELETE`) are programmatically blocked [47].
* **Human-in-the-Loop (HITL) Review**: Wrap high-risk, irreversible, or state-changing tools with review gates or interrupt wrappers that pause execution and allow a human to accept, edit, or reject the proposed tool call parameters [48-51].

---

##### 8. Sandboxing and Isolated Execution
* **Mitigating Infrastructure Risks**: Code-executing agents present severe security risks, including arbitrary file deletion (`rm -rf /`), secret exfiltration, resource hogging, or the "lethal trifecta" (where untrusted web inputs trick an agent with private access into exfiltrating data) [52-55].
* **Fast, Resource-Limited Environments**: Untrusted agent-generated code or shell scripts must be executed inside isolated, ephemeral, and fast-booting sandboxes (e.g., E2B, WebContainers, or server-side containers like Claude Code’s interpreter) [54-57].
* **Containment Bounds**: Sandboxes enforce network access restrictions, file-system isolation, input sanitization middleware, CPU/RAM caps, and automatic teardown to isolate potential malicious exploits or accidental bugs from host systems [54, 55, 58, 59].

---

##### 9. Deterministic Scripts vs. LLM Reasoning Steps
* **When to Use Pure Code / Deterministic Scripts**:
  * For well-defined, low-latency, cost-sensitive, or fixed operations (e.g., invoice parsing in standard formats, mathematical computations, unit conversions, or date arithmetic) [60-62].
  * When operations are fragile, error-prone, or require exact step-by-step consistency where no semantic variation can be tolerated [6, 63].
  * When executing fixed multi-step workflows with known decision branches (e.g., Airflow, AWS Step Functions, or dynamic JavaScript dynamic workflow orchestrators) [60, 61, 64].
* **When to Use an LLM Step**:
  * Only when the task involves high input variability, highly unstructured text, novel scenarios, or open-ended dynamic planning that cannot be pre-scripted [61, 65, 66].
* **Pre-made Utility Scripts**: When a repetitive procedure is needed, provide pre-made executable scripts as local tools rather than asking the LLM to generate code on the fly. Pre-made scripts save tokens, eliminate code-generation latency, and guarantee deterministic execution [67, 68].
