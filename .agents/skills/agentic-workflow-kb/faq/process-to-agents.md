## process-to-agents-1: How do I derive agents, skills, code and checkpoints from a business process model?

- asked 2026-09-26 · notebook "Agentic Workflows" · conversation `9169c090-1402-4ad8-9c51-829d89ac9fb7`
- Sources: Bhagwat & Gienow, Patterns for Building AI Agents (2026); Bhagwat, Principles of Building AI Agents; Koenigstein, AI Agents: The Definitive Guide (O'Reilly, 2025); Albada, Building Applications with AI Agents (O'Reilly, 2025); Bruniaux, claude-code-ultimate-guide: dynamic-workflows.md (GitHub); Osmani, Beyond Vibe Coding (O'Reilly, 2025); Grootendorst & Alammar, An Illustrated Guide to AI Agents (O'Reilly, 2025); Osmani, My LLM coding workflow going into 2026 (addyosmani.com)

**Question**

> Given a business process model with roles (swimlanes), tasks, decision gateways, loops, parallel branches, human approval steps and data artifacts, how do the sources suggest deriving an agentic system from it? Which parts should become agents, tools/skills, deterministic code, orchestration logic and human checkpoints? What granularity is right for an agent? Which model size fits which role (routing by difficulty, cost/latency)? What are the pitfalls of automating an existing human process with agents?

**Answer** (verbatim, citation markers resolve in the table below)

Deriving an agentic architecture from a business process model (such as a BPMN diagram with swimlanes, decision gateways, loops, and human approvals) requires translating static procedural steps into a flexible **organizational design for AI agents** [1, 2].

---

##### 1. How to Derive an Agentic System from a Process Model

To map a process model into an agentic system, analyze each element through the lens of agency, state management, and execution predictability [3-5]:

* **Swimlanes & Roles \\(\rightarrow\\) Specialized Domain Agents:** Swimlanes map directly to agent boundaries [5-7]. Rather than creating a single "mega-agent," group capabilities by organizational function, shared domain knowledge, or specific steps in the business process [5, 7, 8].
* **Tasks & Activities \\(\rightarrow\\) Tools/Skills vs. Agent Subtasks:** Predictable, single-pass operational tasks become **deterministic tools or skills**, while open-ended tasks requiring semantic interpretation or planning become subtasks assigned to an agent [9-11].
* **Decision Gateways \\(\rightarrow\\) Router Nodes & Conditional Edges:** Conditional splits (XOR/OR gateways) map to **router agents or finite state machine (FSM) conditional edges** that inspect state variables to decide the next execution path [3, 12-14].
* **Loops & Feedback Cycles \\(\rightarrow\\) ReAct / Reflection Loops:** Re-work loops map to stateful reasoning-acting-reflection cycles (e.g., ReAct or Actor-Critic patterns) where the agent examines step execution feedback or error traces before retrying [9, 15-17].
* **Parallel Branches \\(\rightarrow\\) Async Execution / Subagent Parallelism:** Independent concurrent swimlanes map to parallel subagent pipelines or message brokers (such as Kafka or Ray actors) that execute asynchronously before merging outputs into a downstream node [18-21].
* **Human Approval Steps \\(\rightarrow\\) Human-in-the-Loop (HITL) Interrupts:** High-stakes approval gates map to explicit state machine checkpoints (pause/resume, edit arguments, or deferred tool execution) [22-25].
* **Data Artifacts \\(\rightarrow\\) Structured State Schemas & Memory Stores:** Documents and data inputs map to typed state schemas, context windows, vector stores (RAG), or persistent databases passed across state graph nodes [12, 21, 26-28].

---

##### 2. Allocation of Process Components

| System Component | What Belongs Here | Rationale & Examples |
| :--- | :--- | :--- |
| **Agents** | Tasks requiring **reasoning, multi-step planning, ambiguity resolution, or natural language generation** [4, 29, 30]. | Inventory specialist, research assistant, code reviewer, customer support agent [31-33]. |
| **Tools / Skills** | Atomic, modular capabilities that **interact with external environments or perform discrete actions** [11, 34, 35]. | Web scrapers, API endpoints, SQL/database lookup scripts, email notification wrappers [11, 36, 37]. |
| **Deterministic Code** | Fully predictable logic, math, schema transformations, and strict input/output formatting [10, 38]. | Log parsing regex, financial currency conversions, JSON schema validators, time-zone math [10, 21, 38]. |
| **Orchestration Logic** | State machines, graph edges, and workflow scripts that control execution flow and data handoffs [3, 13, 26, 39]. | LangGraph state graphs or JavaScript workflow scripts (`agent()`, `parallel()`, `pipeline()`) where orchestrator execution incurs zero token cost [13, 26, 39, 40]. |
| **Human Checkpoints** | Irreversible actions, high-risk financial or security operations, or low-confidence outputs [22, 41-43]. | approving payments, isolating network hosts, reviewing legal/medical claims prior to final submission [22, 25, 44, 45]. |

---

##### 3. Determining the Right Granularity for an Agent

Choosing agent granularity requires balancing **task focus against coordination complexity** [46, 47]:

* **The Monolithic "Mega-Agent" Anti-Pattern:** Placing all tools and responsibilities inside a single prompt increases the tool choices presented to the model, which sharply elevates tool selection errors, dilutes reasoning focus, and leads to context failure modes [8, 48-50].
* **The "Micro-Agent" Anti-Pattern:** Creating an agent for every tiny task introduces severe communication latency, unnecessary inter-agent message passing, high token overhead, and brittle handoffs [46, 47, 51, 52].
* **The "Goldilocks" Principle (Parsimony & Specialization):** Apply the **principle of parsimony**—add only the minimum number of agents necessary [47]. Scope agents around cohesive domain roles (like a human job description), a specific dataset, or a distinct phase in a workflow (e.g., a *Discovery Agent* vs. a *Writing Agent*) [5, 7, 53-55].

---

##### 4. Model Selection & Routing Strategy (Difficulty, Cost, Latency)

Not every node in a process graph requires a flagship reasoning model [56-58]:

* **Large / Frontier Reasoning Models (e.g., GPT-5, Claude 4 Opus, o3/o4-mini):**
  * *Best for:* High-level planning, supervisor/orchestrator routing, complex multi-step reasoning, ambiguous synthesis, and reflection/evaluator roles [56, 59-62].
  * *Trade-offs:* High compute/token costs, higher latency [61, 63].
* **Small / Compact / Open-Weight Models (e.g., 8B–70B parameters, Phi-4, Gemini Flash):**
  * *Best for:* Narrow execution subagents, fast classification, structured text extraction, routine customer queries, and calling local tools [56-58, 64].
  * *Trade-offs:* Reduced zero-shot generalization on ambiguous, novel tasks [58, 65].
* **Dynamic Model Routing:** Route routine steps to small, low-cost models, reserving frontier reasoning models for complex planning or exception handling [57, 63]. Additionally, a lightweight model can propose options (e.g., Tree-of-Thought branches) while a stronger model evaluates them, optimizing cost and time [56].

---

##### 5. Pitfalls of Automating Human Processes with Agents

* **The "70% Problem" & Demo Quality Trap:** Agents quickly handle initial boilerplate and routine steps (70% of the work), but the final 30% (handling edge cases, security, production hardening, and long-term maintainability) requires deep human engineering [66-69].
* **Over-Agentifying Deterministic Logic:** Replacing predictable, rule-based workflows with LLM calls introduces non-determinism, higher latency, unnecessary costs, and auditability problems where simple procedural code or workflow engines would excel [4, 10, 52, 70].
* **Coherent Incorrectness & "Two Steps Back":** Autonomous agents can generate code or decisions that are internally consistent but fundamentally misaligned with business requirements, trapping developers in a cycle where fixing one bug breaks two others [71-73].
* **Async Parallel Coordination Conflicts:** Spawning parallel subagents without shared context leads to mutually incompatible outputs that fail when merged downstream [74-76].
* **Context Rot & Token Bloat:** Dumping entire databases or raw execution traces into a context window degrades reasoning performance ("context rot") while driving up latency and costs [50, 77, 78].
* **Automation Bias & Missing SME Oversight:** Relying strictly on developer evaluations rather than embedding real domain subject matter experts (SMEs) to label data and review live failures leads to unmonitored production errors [79-81].
